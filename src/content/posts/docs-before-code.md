用 AI 写代码，最浪费时间的不是它写错，而是它写对了另一个东西——方向偏了，代码质量再高也得推翻。文档的作用就是把「另一个东西」提前排除掉。

## 一句话说清三份文档的分工

| 文档 | 回答的问题 | 谁最需要它 |
|---|---|---|
| `PRD.md` | 做哪些功能，明确不做哪些 | 你自己，防止范围膨胀 |
| `TECH_DESIGN.md` | 用什么实现，代码怎么组织 | AI，避免它自由发挥选型 |
| `AGENTS.md` | 有哪些硬性规矩不能破 | 每一次对话，相当于常驻约束 |

三者缺一，问题会以不同形式冒出来：缺 PRD 会越做越大，缺 TECH_DESIGN 会换来换去，缺 AGENTS.md 会每次都要重新交代一遍。

## PRD：先把「不做」写下来

需求文档最容易写错的地方，是只列功能不划边界。比如「个人网站要有博客」，这句话可以做出十种东西：带后台的 CMS、带评论的社区、只读的文章列表。

我的写法是先写一段目标，再用一张表把功能拆到「能验收」的粒度，最后单独一节写**不做的事**：

- 不做注册、评论、点赞；
- 不接后端数据库；
- 不做多语言。

这三条写下来，后面所有关于「要不要加个 XX」的讨论都有了裁决依据。AI 也不会热情地给你补一堆用不上的功能。

## TECH_DESIGN：把选型理由写进去

只写「用 React + Vite」不够。真正有用的是**为什么不用别的**：

- 为什么不用 Next.js：没有动态内容，SSR 带来的是构建复杂度而不是收益；
- 为什么不用组件库：深色定制成本高于手写，产物还更大；
- 为什么用 HashRouter：纯静态托管没有 rewrite，BrowserRouter 刷新就 404。

把这些写进文档，AI 在后续改动里就不会「好心」帮你换回 BrowserRouter——它知道那是有意为之。

## AGENTS.md：写规矩，不写教程

这份文件的读者是 AI，所以全部用祈使句和禁止项，不要解释概念：

```md
- TypeScript 严格模式，不使用 any
- 样式全部走 Tailwind，不新增 .css 文件
- 路由只集中在 App.tsx 声明
- 不要引入后端，留言表单是前端演示
- 提交信息格式：feat: xxx / fix: xxx / docs: xxx
```

像「代码要整洁」这种话没有信息量，删掉。写「组件文件名 PascalCase，工具文件 camelCase」才有用。

## 一个真实对比

同一个插件项目，第一版我只给了三行需求，结果生成出来的目录结构是「一个 content.js 装下全部逻辑」，八百多行，改一处要读全文。

第二版先花四十分钟写需求拆解与职责划分，再写一句「content.js 只负责采集，不负责下载；background.js 只负责中转与调度，不解码图片」。生成出来的就是六个文件、职责清晰的结构，一次跑通。

四十分钟换一次跑通，很划算。

## 写到什么程度就够

判断标准很简单：**把文档给一个没参与过讨论的人，他能不能照着做出来**。

- 功能能列出验收条件；
- 技术选型有理由；
- 目录结构画得出来；
- 数据长什么样有类型定义。

到这四步就可以停。再往下写就是在替 AI 写代码了，反而限制它的实现空间。

## 什么时候可以不写

脚本、demo、一次性验证想法，直接写。文档的成本要在「会返工」的项目上才收得回来。判断依据是：这个项目你会不会改第二次。会，就写。
